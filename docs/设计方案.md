# 记账 App 设计方案（v1 · 待确认）

> 面向设备：荣耀/华为系 Android（MagicOS / HarmonyOS 4.x）
> 采集权限：免 root（通知 + 无障碍 + 截图 OCR）
> 数据归属：纯本地
> 第一版范围：自动记账核心链路（微信 / 支付宝）

---

## 0. 先决问题：你的手机到底能不能装 APK

这一条决定整个技术路线，必须先澄清：

| 机型 / 系统 | 内核 | 能否装 Android APK | 路线 |
|---|---|---|---|
| **荣耀 HONOR**（MagicOS 7/8/9） | Android | ✅ 能 | 本方案直接可用 |
| 华为 HarmonyOS 4.x / 4.2 | 基于 AOSP | ✅ 能 | 本方案直接可用 |
| **华为 HarmonyOS NEXT（5.0，纯血鸿蒙）** | 自研 | ❌ **不能** | 必须改用 ArkTS/ArkUI 重写，采集能力大幅受限 |

**请确认你的机型**（设置 → 关于手机 → 看"HarmonyOS 版本"或"MagicOS 版本"）。
下面全部内容默认你走的是 **Android 兼容** 那条路。

## 1. 设计输入：三个参考项目给我们的结论

### 必须继承的经验（血的教训）

1. **微信不发支付通知** —— 只能靠"支付成功页 + 截图 OCR"。这是本项目最复杂的一条链路。
2. **支付结果页是异步渲染的** —— 单次读取必然失败，必须在 120ms / 380ms / 900ms 三个时间点反复探测（AutoLedger 的做法）。
3. **无障碍节点可能完全不存在**（微信支付页自绘）—— OCR 是必需项，不是可选项。
4. **通知字段要全合并** —— title / text / bigText / subText / summaryText / tickerText，金额经常只出现在 bigText 或 subText 里。
5. **噪音词库决定成败** —— "立减券/待领取/点我抽奖/任务达标/最高立减"这类营销文案必须过滤，否则误记率极高。
6. **国产 ROM 会吞掉通知监听服务** —— 需要自检 + 明确引导，而不是假装它一直活着。

### 必须避开的坑（三个项目的数据层都有硬伤）

| 问题 | 谁犯的 | 我们的做法 |
|---|---|---|
| 金额用 `Double`/`REAL` 存 | WhereIsMyMoney | **一律 INTEGER 存"分"** |
| 全库 0 索引 0 唯一约束 | WhereIsMyMoney | 关键查询路径全部建索引 |
| 精心写的 `CONFLICT_IGNORE` 因无唯一索引而失效 | AutoLedger | 唯一约束与去重逻辑对齐并有单测 |
| 指纹固定按分钟截断 → 跨分钟漏判 / 同分钟误杀 | AutoLedger | 滑动时间窗 + 融合判定，不依赖固定截断 |
| 统计页只算通知数据，导入数据被排除 | WhereIsMyMoney | 统计唯一数据源，口径集中定义 |
| 规则硬编码在代码里，用户无法调整 | 三个都是 | **规则外置为可编辑配置（本项目核心）** |
| 保活直写 `Settings.Secure`、无视用户开关 | AutoLedger | 只做自检与引导，不越权改系统设置 |

## 2. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Kotlin | 简洁、协程一流、Compose 必需 |
| UI | Jetpack Compose + Material 3 | 你要"UI 完全自定义"，Compose 做主题系统最省力 |
| 数据库 | Room（SQLite）+ WAL | 编译期校验 SQL、原生 Flow 支持、迁移可控 |
| 异步 | Coroutines + Flow | |
| 架构 | 单模块多包分层（Domain / Data / Capture / Ui） | MVP 阶段单模块，避免过度工程；边界靠包约束 |
| minSdk | 26（Android 8.0） | 覆盖广；截图 API(30+) 运行时判断降级 |
| compileSdk / targetSdk | 34 | 本机 SDK 现有版本 |
| OCR | **ML Kit 中文 bundled 离线模型**（已实测：正式包 13.77 MB） | 打包进 APK，**不需要 GMS**；详见 §6.3 |
| 构建 | 本机命令行 Gradle 8.7 + JDK 17 + SDK 34 | **已实测：80 秒出 APK，无需 Android Studio** |

## 3. 架构总览

```
┌─────────────────── 采集层 Capture（可插拔通道） ──────────────────┐
│  NotificationChannel   通知监听（全字段合并）                      │
│  AccessibilityChannel  无障碍文本（多窗口遍历 + 三段延时探测）      │
│  OcrChannel            截图 + 离线 OCR（微信专用兜底）             │
│  ManualChannel         手动记账 / 通知栏 RemoteInput 补录          │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓ 统一产出 RawEvidence（原文 + 来源 + 时间 + 通道）
┌─────────────────── 解析与融合层 Engine（自研核心） ────────────────┐
│  1. RuleEngine        规则匹配：金额/方向/商户/分类/忽略词          │
│  2. EvidenceMerger    多路证据融合（不是简单去重）                 │
│  3. Scorer            置信度打分（权重可配置）                     │
│  4. GateKeeper        入账闸门 → 自动入账 / 进待确认               │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓
┌─────────────────── 数据层 Data（Room） ──────────────────────────┐
│  raw_evidence / transactions / transaction_evidence              │
│  categories / category_rules / accounts / rule_profiles          │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓ Flow
┌─────────────────── UI 层 Ui（Compose M3 + 主题系统） ─────────────┐
│  首页 / 流水 / 待确认 / 统计 / 设置(通道·规则·主题·备份)          │
└──────────────────────────────────────────────────────────────────┘
```

## 4. 数据模型（你的 DIY 重点 ①）

### 4.1 表结构草案

```sql
-- ① 原始证据：不可变、永久留档。存在的意义是"规则回放"和误判追溯。
CREATE TABLE raw_evidence (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  channel        TEXT NOT NULL,        -- NOTIFICATION / ACCESSIBILITY / OCR / MANUAL
  source_key     TEXT NOT NULL,        -- WECHAT / ALIPAY / UNIONPAY / MANUAL
  package_name   TEXT NOT NULL,
  title          TEXT,
  raw_text       TEXT NOT NULL,
  captured_at    INTEGER NOT NULL,     -- 抓取时刻
  occurred_at    INTEGER,              -- 解析出的交易时刻
  process_state  TEXT NOT NULL,        -- NEW / MERGED / PARSED / DISCARDED
  discard_reason TEXT,                 -- 命中了哪条忽略规则（调试关键）
  parse_snapshot TEXT,                 -- 当时解析结果的 JSON 快照
  rule_version   INTEGER               -- 用了哪一版规则 → 可回溯"当时为什么判错"
);
CREATE INDEX idx_evidence_time   ON raw_evidence(captured_at DESC);
CREATE INDEX idx_evidence_source ON raw_evidence(source_key, captured_at DESC);
CREATE INDEX idx_evidence_state  ON raw_evidence(process_state, captured_at DESC);

-- ② 交易：正式账目。金额一律整数分。
CREATE TABLE transactions (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  amount_cents  INTEGER NOT NULL CHECK(amount_cents >= 0),
  direction     TEXT NOT NULL,         -- EXPENSE / INCOME / TRANSFER
  merchant      TEXT NOT NULL DEFAULT '',
  category_id   INTEGER REFERENCES categories(id) ON DELETE SET NULL,
  account_id    INTEGER REFERENCES accounts(id)   ON DELETE SET NULL,
  note          TEXT NOT NULL DEFAULT '',
  occurred_at   INTEGER NOT NULL,
  created_at    INTEGER NOT NULL,
  status        TEXT NOT NULL,         -- PENDING(待确认) / CONFIRMED / DELETED
  confidence    REAL NOT NULL DEFAULT 1.0,
  source_key    TEXT NOT NULL,
  batch_id      INTEGER                -- 导入批次（历史账单导入用）
);
CREATE INDEX idx_tx_time     ON transactions(occurred_at DESC, id DESC);
CREATE INDEX idx_tx_status   ON transactions(status, occurred_at DESC);
CREATE INDEX idx_tx_category ON transactions(category_id, occurred_at DESC);
CREATE INDEX idx_tx_merchant ON transactions(merchant, occurred_at DESC);

-- ③ 证据↔交易 关联：一笔交易可能由多条证据合成（这是"融合"的落点）
CREATE TABLE transaction_evidence (
  transaction_id INTEGER NOT NULL REFERENCES transactions(id) ON DELETE CASCADE,
  evidence_id    INTEGER NOT NULL REFERENCES raw_evidence(id) ON DELETE CASCADE,
  role           TEXT NOT NULL,        -- PRIMARY / SUPPORTING
  PRIMARY KEY(transaction_id, evidence_id)
);

-- ④ 分类（用户可编辑，支持二级）
CREATE TABLE categories (
  id, name, icon, color, parent_id, direction, sort_order, is_system
);

-- ⑤ 分类规则（商户/关键词 → 分类），优先级可调
CREATE TABLE category_rules (
  id, match_text, match_type,          -- CONTAINS / REGEX / EQUALS
  category_id, priority, enabled, hit_count   -- hit_count 用于评估规则有效性
);

-- ⑥ 账户（银行卡/花呗/微信零钱/现金）—— MVP 可先只留一张默认账户
CREATE TABLE accounts (id, name, type, icon, color, initial_balance_cents, is_archived);

-- ⑦ 规则档案：用户编辑的规则历史，可回滚
CREATE TABLE rule_profiles (id, name, version, content_json, updated_at, is_active);
```

### 4.2 为什么这样设计

- **两级存储（证据 / 交易）** 借鉴 AutoLedger，但改进点是 **证据与交易是多对多**：通知抓到一半、OCR 补上另一半，两条证据指向同一笔交易，可追溯。
- **金额全整数分**，统计永不丢精度。
- **`rule_version` + `parse_snapshot`** 是"规则回放调试"的地基：改规则后能对历史全部证据重跑，告诉你哪几笔会变、哪几笔是误判。
- **统计口径集中在一处定义**（Domain 层单一函数），不允许多个页面各算各的。

## 5. 识别规则引擎（你的 DIY 重点 ②，本项目灵魂）

### 5.1 规则是一份可编辑的 JSON，不是代码

```jsonc
{
  "version": 3,
  "autoConfirmThreshold": 0.82,
  "sources": [
    {
      "key": "ALIPAY",
      "packageNames": ["com.eg.android.AlipayGphone"],
      "titleKeywords": ["支付宝", "支付助手", "账单"],
      "amountPatterns": [
        "[¥￥]\\s*([0-9]{1,9}(?:\\.[0-9]{1,2})?)",
        "([0-9]{1,9}(?:\\.[0-9]{1,2})?)\\s*元"
      ],
      "incomeKeywords": ["收款成功", "到账", "退款", "收到转账"],
      "expenseKeywords": ["支付成功", "付款成功", "消费", "扣款成功"],
      "ignoreKeywords": ["优惠券", "立减", "待领取", "点我抽奖", "任务达标", "最高"],
      "merchantPatterns": ["商户[：:]\\s*(.+?)\\s", "向(.+?)付款"],
      "resultPageMarkers": ["payresult", "paymentresult", "nrespageactivity"]
    },
    {
      "key": "WECHAT",
      "packageNames": ["com.tencent.mm"],
      "titleKeywords": ["微信支付", "微信收款"],
      "channelHint": "OCR",            // 微信主走 OCR
      "pageClassMarkers": ["walletpay", "payresult", "remittance"],
      "browsingPageExcludes": ["交易详情", "账单详情", "交易单号", "全部会话"]
    }
  ],
  "categoryRules": [
    { "match": ["瑞幸","星巴克","蜜雪","咖啡","奶茶","外卖","餐饮"], "category": "餐饮" },
    { "match": ["地铁","公交","滴滴","打车","加油","停车"],        "category": "交通" },
    { "match": ["电影","游戏","steam","K歌"],                      "category": "娱乐" },
    { "match": ["房租","物业","水电"],                             "category": "居住" }
  ],
  "weights": {
    "channelNotification": 0.55, "channelAccessibility": 0.50, "channelOcr": 0.45,
    "hasAmount": 0.15, "hasMerchant": 0.12, "strongKeyword": 0.20,
    "amountOutOfRange": -0.30
  },
  "gates": {
    "missingAmountGoesPending": true,
    "missingMerchantGoesPending": true,
    "largeExpenseMultiplier": 2.0,     // 超过历史最大支出 2 倍 → 强制待确认
    "duplicateWindowSeconds": 90
  }
}
```

### 5.2 引擎的四个能力

1. **热更新** —— 改规则立即生效，不需要重新编译 App。
2. **App 内可视化编辑** —— 关键词以标签形式增删，正则可在线测试（贴着输入框显示实时匹配结果）。
3. **规则回放** —— 一键把当前规则在全部历史证据上重跑，输出：新增识别 N 笔、丢失 M 笔、与原结果不一致的清单（逐条对比）。**这是把识别率做上去的唯一实用手段。**
4. **导入导出** —— 纯文本 JSON，可备份、可分享、可版本管理。

### 5.3 证据融合算法（竞品都没有）

```
输入：时间窗内（±90s）同来源的多条证据
判定同一笔的条件：金额一致或有一方缺失，且方向不冲突
合并策略（字段级择优）：
  amount      → 双方都有且一致则采用；冲突则取置信度高的一方，并降级为待确认
  merchant    → 取更具体的一条（"瑞幸咖啡" 优于 "瑞幸"）
  occurred_at → 取更早的
  direction   → 冲突时以强关键词证据为准，并降级为待确认
  evidence    → 全部保留关联，形成完整证据链
输出：一条交易 + N 条证据
```

## 6. 采集通道（免 root 三通道）

### 6.1 通知通道 NotificationChannel
- `NotificationListenerService`，合并 title/text/bigText/subText/summaryText/infoText/tickerText 全部字段。
- 服务健康自检：定期确认 `onListenerConnected` 是否真的连着；**荣耀/华为需引导用户手动重绑**（页面内提供一键跳转 + 图文步骤），不做越权改系统设置。

### 6.2 无障碍通道 AccessibilityChannel
- 多窗口遍历（activeWindow + getWindows()），文本去重上限 500 条、深度 12。
- **三段延时探测**：Activity 切换后 120 / 380 / 900 ms 各读一次。
- 排除浏览页（"交易详情/账单详情/交易单号"等标记）与"待收款/待确认"页。

### 6.3 OCR 通道 OcrChannel（微信的生命线）
- 触发条件：检测到微信支付页特征（页面类名 + 文案）→ 1.2s / 3.2s 两次尝试；12 秒内只触发一次；截图前再次确认微信仍在前台。
- 截图 API：`AccessibilityService.takeScreenshot`（Android 11+），失败则降级到通知栏提醒人工补录。
- **OCR 引擎：已实测选定 ML Kit 中文 bundled 模型**（`com.google.mlkit:text-recognition-chinese:16.0.1`）
  - 模型打包进 APK，**不依赖 GMS** —— 你的荣耀/华为没有谷歌服务也能用。
  - **本机真实构建实测**（同一份代码，只改构建配置）：

    | 构建配置 | APK 体积 |
    |---|---|
    | debug · 4 个 ABI · 不混淆 | 51.28 MB |
    | debug · 仅 arm64-v8a | 22.63 MB |
    | **release · 仅 arm64-v8a + R8 混淆 + 资源压缩** | **13.77 MB** ✅ |

  - 体积构成：native 库 10.6 MB（仅 arm64）+ 混淆后 dex + 模型 assets 仅 2.37 MB。
  - **结论：正式包 13.77 MB，完全可接受**。（参考项目 AutoLedger 的 48 MB 是因为它既没做 ABI 过滤也没开混淆。）
  - ⚠️ **构建硬性要求**：`ndk { abiFilters += "arm64-v8a" }` + release 开 `isMinifyEnabled`/`isShrinkResources`。不做这两件事，包会直接膨胀到 51 MB。
  - 备选方案 B（PaddleOCR PP-OCRv5 + ncnn）原本的优势是体积小，**实测后这个优势已不存在**，仅作为"完全自主可控"的远期选项，接口层预留替换点即可。

### 6.4 手动通道 ManualChannel
- App 内快速记账 + 通知栏 `RemoteInput` 补录（识别到交易但没抓到金额时，直接在通知里输入金额）。
- 通知带「误识别·删除」按钮，一键撤销错误入账。

## 7. UI 与主题（你的 DIY 重点 ③）

### 7.1 页面结构（MVP 只做粗体这四个 + 权限引导）

- **权限引导页**：通知监听 / 无障碍 / 电池优化 / 后台锁定，逐项图文引导 + 实时状态检测（做没做对一眼可见）。
- **首页**：本月收支大数字 + 今日流水 + 悬浮快速记账按钮。
- **流水页**：按日分组，支持搜索/筛选/编辑/删除。
- **待确认页**（灵魂）：低置信度记录集中处理，一键确认 / 改分类 / 改金额 / 删除 / 标记为噪音（标记后自动进忽略词库）。
- 统计页、预算页、多账本 → 二期。

### 7.2 主题系统（"UI 完全自定义"的落点）
- 颜色、圆角、间距密度、正文字号、卡片样式全部抽成一份 **主题 JSON**，App 内可调，可导入导出。
- 内置 3 套预设（极简白 / 暗夜 / 信息密集）起步。
- 不引入重型 UI 库，避免"看着好看但改不动"。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 荣耀 MagicOS 后台限制 | 监听服务被杀，漏记 | 权限引导页 + 服务自检 + 漏抓时通知栏提醒；不做越权保活 |
| 微信支付页抓不到（自绘/无节点） | 微信漏记 | OCR 兜底 + 失败时降级为"手动补录提醒" |
| OCR 识别错数字 | 记错金额 | OCR 结果一律先入待确认，不自动确认（通道权重最低） |
| 支付 App 改版 | 规则失效 | 规则外置可自助修改 + 回放调试 |
| 同一笔被多渠道抓到 | 重复记账 | 证据融合 + 滑动时间窗 + 同额重复闸门 |
| 纯血鸿蒙装不了 APK | 全盘推翻 | **见 §0，请先确认机型** |
| 构建配置漏掉 ABI 过滤/混淆 | 安装包膨胀近 4 倍（51MB） | 构建配置固化为 arm64-v8a + R8，已实测 13.77 MB |

在等你确认方案期间，我先把有决策风险的技术点验证掉了，避免开工后才发现路走不通：

| 验证项 | 结果 |
